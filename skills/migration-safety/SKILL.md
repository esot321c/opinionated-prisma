# Migration Safety

## Rules

- Never run `prisma migrate dev` against production. Use `prisma migrate deploy`.
- Preview with `prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --script` (Prisma 7 removed `--from-url`/`--to-url`; the shadow database is set in `prisma.config.ts`).
- Use `--create-only` when you need to hand-edit the migration SQL before applying (partial indexes, `CONCURRENTLY`, constraint validation).
- New columns must be nullable or have a default. Adding a `NOT NULL` column without a default fails on any non-empty table.
- One concern per migration. Don't combine schema changes with data backfills in the same migration file.

## Workflow

```
1. Edit schema.prisma
2. prisma migrate dev --create-only    # generates SQL, does not apply
3. Review/edit the generated SQL        # add CONCURRENTLY, partial indexes, etc.
4. prisma migrate dev                   # apply locally
5. prisma generate                      # Prisma 7's migrate dev no longer runs it
6. Test against seed data
7. prisma migrate deploy                # apply in staging/production
```

## Safe Patterns

### Adding a Required Column to an Existing Table

Do NOT add it as `NOT NULL` in one step. Prisma will generate a migration that fails on existing rows.

```
Step 1: Add as optional
  referenceNumber String? @map("reference_number")

Step 2: migrate dev --create-only, apply

Step 3: Backfill
  UPDATE matters SET reference_number = 'LEGACY-' || id WHERE reference_number IS NULL;

Step 4: Change to required
  referenceNumber String @map("reference_number")

Step 5: migrate dev --create-only, verify the generated ALTER uses SET NOT NULL
```

On a large table, `SET NOT NULL` scans the whole table under an ACCESS EXCLUSIVE lock. First add `CHECK (reference_number IS NOT NULL) NOT VALID`, `VALIDATE` it, then `SET NOT NULL` (the scan is skipped), then drop the CHECK.

### Adding an Index

Prisma generates `CREATE INDEX`, which blocks writes to the table for the whole build. `CONCURRENTLY` avoids that, but it is slower, cannot run inside a transaction, and leaves an INVALID index if it fails. Choose by the situation:

| Situation | Use | Why |
|---|---|---|
| Existing production table serving live traffic | Usually `CONCURRENTLY` | Blocking writes for the build is an outage |
| New table, before the application uses it | Regular `CREATE INDEX` | Nothing writes to it yet |
| Local development or tests | Regular | No traffic to protect |
| Maintenance window with writes paused | Usually regular | Faster, and nothing is blocked |
| Index must be created inside an atomic transaction | Regular | `CONCURRENTLY` cannot run in a transaction |

For the first case, edit the migration to use `CONCURRENTLY`:

```sql
-- Generated by Prisma (edit this):
-- CREATE INDEX "idx_matters_client_id" ON "matters"("client_id");

-- Replace with:
CREATE INDEX CONCURRENTLY "idx_matters_client_id" ON "matters"("client_id");
```

How Prisma applies migration SQL on PostgreSQL depends on the version:

- Prisma 7.4 and later splits `migration.sql` into statements and sends each one separately. `CREATE INDEX CONCURRENTLY` works in any migration, but a migration is not atomic: if a statement fails, earlier statements stay applied and the migration is marked failed (P3018). Recover by hand, then `prisma migrate resolve`.
- Prisma 7.3 and earlier sent the file as one multi-statement query, which PostgreSQL runs as one implicit transaction. `CONCURRENTLY` worked only in a migration containing that single statement.

Put each `CREATE INDEX CONCURRENTLY` in its own migration. If it fails, it leaves an INVALID index: `DROP INDEX CONCURRENTLY` it before retrying.

### Adding a Constraint Safely

```sql
-- In custom migration SQL:
ALTER TABLE matters ADD CONSTRAINT chk_total_positive CHECK (total >= 0) NOT VALID;
-- Separate migration or script:
ALTER TABLE matters VALIDATE CONSTRAINT chk_total_positive;
```

`NOT VALID` applies the constraint to new rows immediately without scanning existing rows. `VALIDATE` scans existing rows without holding an exclusive lock.

## Dangerous Operations

| Operation | Risk | Safe Alternative |
|---|---|---|
| Add `NOT NULL` column without default | Fails on any non-empty table | Add nullable, backfill, then set `NOT NULL` |
| `CREATE INDEX` on large table | Blocks writes (not reads) for the whole build | `CREATE INDEX CONCURRENTLY` via `--create-only` |
| Drop column | Breaks running code during deploy | Stop reading column in code first, deploy, then drop in next migration |
| Rename column | Breaks running code | Add new column, copy data, update code, drop old column across multiple deploys |
| Add constraint | Full table scan with lock | `NOT VALID` then `VALIDATE` separately |

## Rollback Strategy

- Generate a down migration with `prisma migrate diff --from-schema prisma/schema.prisma --to-migrations prisma/migrations --script > down.sql`, store it as `down.sql` next to `migration.sql`, apply it with `prisma db execute --file`, and for a failed migration run `prisma migrate resolve --rolled-back <name>`.
- For additive-only migrations (new tables, new nullable columns), rollback is rarely needed.
- For column drops or type changes, keep a backup of the column data before applying.

## Correct

```
migrations/
  20260515120000_add_reference_number/
    migration.sql          # ALTER TABLE ADD COLUMN reference_number VARCHAR
    down.sql               # ALTER TABLE DROP COLUMN reference_number
  20260515120001_backfill_reference_number/
    migration.sql          # UPDATE matters SET reference_number = ...
  20260515120002_require_reference_number/
    migration.sql          # ALTER TABLE ALTER COLUMN reference_number SET NOT NULL
```

## Incorrect

```
migrations/
  20260515120000_add_reference_number/
    migration.sql
    # Contains: ALTER TABLE ADD COLUMN reference_number VARCHAR NOT NULL DEFAULT ''
    # NOT NULL DEFAULT '' is fast on PostgreSQL 11+ (the default is stored in metadata),
    # but it writes a fake value into every existing row and hides missing data.
    # Backfill real values instead.
```
